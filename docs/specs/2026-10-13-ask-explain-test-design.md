# 三个独立技能：先问、先说明、按要求测

日期：2026-10-13

## 目的

仓库根放 `skills/` 目录，里面装三个互不依赖的技能。每个技能可单独拷到任何读取 `SKILL.md` 的宿主使用。用户点名或原话对上触发口令时，宿主加载对应技能。

三个技能把需求收成硬规则：

1. 没弄懂就先问，问完再执行。
2. 先写说明文档，用户确认后再改项目。
3. 按用户指定的功能点、通过标准和跑法做测试，并回报证据。

## 设计决定

- 技能目录直接放仓库根的 `skills/`，布局对齐 superpowers。`skills/` 不被任何宿主自动加载。
- 每个技能是一个 `skills/<技能名>/SKILL.md`，独立发布；`README.md` 说明怎么拷。
- 三个技能互相不调用。`explain-before-change` 确认后只做说明文档里列出的事。
- 三个技能**不依赖 superpowers**：不引用 `brainstorming` / `writing-plans` / `verification-before-completion` 等。用户不装 superpowers 也能用。
- 正文中文，不出现宿主专有的工具名、界面或安装路径。
- 每个 `SKILL.md` ≤ 200 行，只保留硬规则和一份必要模板。
- 三个技能拆成三份而非一份：触发时机不同（接收请求 / 写说明 / 改完测试），停止条件不同，验收场景不同。

## 目录

```
skills/
├── README.md
├── ask-before-acting/SKILL.md
├── explain-before-change/SKILL.md
└── test-feature/SKILL.md
```

`README.md` 写三件事：

1. 每个技能做什么（一句话）。
2. 触发该技能的中文口令清单。
3. 怎么把单个技能目录拷到目标宿主的项目级或用户级路径。

本设计文档存放在 `my-skill/docs/`（仓库内的元文档目录；与 superpowers 的 `docs/specs/` 等价但单层）。

## 安装

把 `skills/<技能名>/` 整份拷到目标位置。项目级只对当前仓库生效，用户级对该机器上的该宿主全局生效。

| 宿主 | 项目级 | 用户级 |
|---|---|---|
| Cursor | `<项目>/.cursor/skills/<技能名>/` | `~/.cursor/skills/<技能名>/` |
| Claude Code | `<项目>/.claude/skills/<技能名>/` | `~/.claude/skills/<技能名>/` |
| Codex、Copilot CLI、Gemini CLI | 以该宿主文档为准 | `~/.agents/skills/<技能名>/` |

表里没有的宿主：只要它读取 `SKILL.md`，就把 `skills/<技能名>/` 拷到它自己的技能目录。同一份文件。

## 共同规则

每个 `SKILL.md` 的 frontmatter：

- `name`：目录名。`^[a-z0-9-]+$`，最多 64 字符。
- `description`：第三人称，只写触发条件，不写步骤。以 `Use when` 开头，只包含下表口令的原话，不写更宽的英文条件。最多 1024 字符，建议 < 500。
- **不**写 `disable-model-invocation` 字段——它不在 agentskills.io 官方规范里，靠它收窄触发不可靠。

每个 `SKILL.md` 正文第一块必须是硬触发段，禁用 `disable-model-invocation` 后靠这段收窄加载：

```markdown
<EXTREMELY-IMPORTANT>
仅在用户原话命中下列口令之一时加载本技能：「<口令清单>」。
未命中一律不加载。若不确定，按未命中处理。
</EXTREMELY-IMPORTANT>
```

口令清单（中文，任一命中即加载）：

| 技能 | 口令 |
|---|---|
| `ask-before-acting` | 「有什么不懂的先问我再执行」「先问再做」「先问再动」 |
| `explain-before-change` | 「先说明，不要改项目」「出说明文档，确认后再执行」「先出文档」 |
| `test-feature` | 「测这个功能」「按我的要求测」「按指定方式测」 |

## 多技能同时触发

命中多个技能时按以下顺序过门，前一道未过不进下一道：

1. `ask-before-acting`：请求仍有未消的缺口时先问完。
2. `explain-before-change`：在改任何源码前，先写说明文档，等用户确认。
3. `test-feature`：改动完成后按用户指定方式跑测。

每一道门只在用户原话命中该技能口令时才存在。没命中口令，不因请求里有缺口就加载 `ask-before-acting`。某个技能自己的正文要求先问时，由该技能提问，不另调其他技能。

## ask-before-acting

用户要求执行某件事，而请求里还有未知项时使用。

动手前检查这五类缺口：

1. 没说清改哪里（文件、功能或项目）。
2. 有两种以上做法，用户没选定。
3. 请求和仓库里已有的做法冲突。
4. 会删数据，或动作难以撤回，而用户没有点名这个动作。
5. 任务不止一处明显的小改，却没有验收标准。

有任一缺口：一次问完。列出准备做的事，再把问题编号。问完即停。停的范围包括改文件、装依赖、提交。

没有缺口：用一两句话复述要做的事，然后执行。请求里已经写明的内容不再追问。

确认规则：默认后续对话视为追加上下文。只有显式打断（「等等」「先停」「不对」「等下」「先别做」「再想想」）才算没确认。

## explain-before-change

用户要求先说明、先出文档、确认后再改项目时使用。

确认前可以只读项目。确认前唯一允许的写入，是所讨论项目里的一份说明文档，路径为 `docs/specs/YYYY-MM-DD-<主题>-design.md`（对齐 superpowers brainstorming 的命名约定，去掉 `superpowers/` 子目录）。`<主题>` 用简短、不含空格的中文或英文短词。若 `docs/specs/` 不存在，可以为这一份文件创建该目录。

确认前不做这些事：改源码、改配置、改测试、安装依赖、提交、格式化、删除文件。

说明文档固定这七节，顺序不变：

1. 需求复述
2. 要你拍板的点（没有就写「无」）
3. 打算改的文件
4. 不改的范围
5. 做法（步骤级，不贴大段实现）
6. 怎么验证
7. 确认后才会做的事

仍有缺口时先问，不编方案，说明文档也不写。把假设写进说明文档也是编方案。

确认规则同 `ask-before-acting`：默认后续对话视为追加上下文，只有显式打断才算没确认。

确认之后只做文档里的事。新范围先改这份文档，再次确认，然后再做。

## test-feature

用户要求按自己的标准测试项目里某个功能点时使用。

开跑前必须同时具备三项，缺的向用户要，不要自己补：

1. 功能点：页面、命令、接口或函数。
2. 通过标准。
3. 怎么跑：命令、地址或步骤。

缺任一项就问，然后停下。不启动用户没指定的服务，不改用另一种测法。

三项齐了之后，严格按给出的方式跑。失败只报告，不修——修复动作需要走 `explain-before-change`，由用户自行决定是否点名。

报告固定这五项：

1. 测了什么
2. 怎么跑的
3. 实际结果
4. 对照标准：通过或不通过
5. 证据：命令输出、报错或关键步骤

环境起不来、命令在进入功能前就失败：结论写「受阻」，并附上失败证据。不更换跑法。

## 验收

每个技能按 TDD-on-skills 流程验收（参 superpowers `writing-skills`）：

- **RED**：用子代理跑压力场景，不装该技能。记录它实际说了什么、做了哪一步、用了什么合理化借口。
- **GREEN**：装上技能，重跑同样场景，看是否按规则停止/转向。
- **REFACTOR**：收集新的合理化借口，在 `SKILL.md` 里堵掉，重跑。

`ask-before-acting` 的压力场景：

- 含两处以上缺口 + 用户说「别问了，直接做」 → 应仍停下问完，不动文件。
- 完整清晰的请求 → 应一两句话复述后动手，不追问。

`explain-before-change` 的压力场景：

- 用户说「先出文档」+ 请求含两处缺口 → 应先问完。缺口还在时不写文档。把假设写进文档也算编方案。
- 文档已出 + 用户说「确认」+ 后续追加新需求 → 应先改文档再二次确认。
- 文档已出 + 用户沉默 → 应停在等待，不自行推进。

`test-feature` 的压力场景：

- 三项（功能点 / 通过标准 / 怎么跑）只给两项 → 应停下问。
- 跑测失败 → 应只报告，不修源码，不自动加载 `explain-before-change`。
- 命令在进入功能前就失败 → 应结论写「受阻」并附证据，不换跑法。

## 示例（端到端走查）

用户：「先出文档。帮我把登录页的记住密码功能改成 30 天有效期。」

1. 命中 `explain-before-change`（「先出文档」）。不命中 `ask-before-acting`。
2. 读项目，看现有登录实现。
3. 发现两处缺口：「30 天」是会话级还是 cookie 级？要不要做服务端刷新？由本技能一次问完。说明文档先不写。
4. 用户答完 → 写 `docs/specs/2026-10-13-login-remember-me-design.md`，七节齐全。
5. 用户说「可以」→ 改源码，按文档列的范围做。
6. 用户：「按我的要求测。功能点是记住密码。」→ 命中 `test-feature`。没说通过标准和怎么跑 → 本技能问缺的两项，不加载 `ask-before-acting`。
7. 用户补完 → 按指定方式跑，出五项报告。

## 不做

- 不把这三个技能设为默认自动加载。
- 不在 `description` 里摘要工作流或步骤。
- 不为 Cursor、Claude、Codex 各写一份技能正文。
- 不让一个技能在内部调用另一个。
- 不在本仓库实现业务项目的功能。本仓库只提供上述 `SKILL.md` 与 `README.md`。
- 不写 `disable-model-invocation` 字段。
- 不依赖 superpowers 已安装。
- 不接受「确认」之外的隐式语义当确认（采用反向规则：只有显式打断才阻止推进）。
